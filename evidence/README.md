# Run evidence

[`index.json`](index.json) is the single repository entry point for run records. Follow each `manifestPath` to a run, then its `attempts` paths. The 2026-09-27 historical records point to existing fixture commits and native session IDs. Ten conversations have published sanitized session assets and recorded hashes; four superseded attempts have no imported assets. All historical attempts remain incomplete because exact request mappings, installed composition, and independent review have not been imported. Do not treat a branch tip or a native session ID as complete evidence.

This is a version 1 JSON format with Markdown scenario and review files. Paths in JSON are repository relative. `unknown` values use `{ "state": "unknown", "reason": "..." }`; record missing facts this way instead of inferring them. A nullable commit or asset locator needs a reason in the attempt's outcome, recovery gaps, or limitations. Do not replace an earlier attempt after a retry or intervention.

Use the [project-run guide](../docs/simulation-workflow.md) for the procedure learned from the pilot and the [scenario template](scenarios/template.md) for a new brief. This file owns the evidence contract; those guides add no actor launcher or grading policy.

## Records and links

| Location | Owner |
| --- | --- |
| `index.json` | Small discovery list with run IDs, manifest paths, summaries, evidence status and review status. This is the future website's static entry point. |
| `runs/<run-id>/run.json` | Run date, required actor model and effort, release prerequisites with evidence sources, attempt paths, aggregate evidence/review status and limitations. |
| `runs/<run-id>/attempts/<attempt-id>.json` | Branch and full Git SHAs; scenario revision; ordered, delivered requests with native event locators and before/after SHAs; sessions and per-turn requested/effective settings and deviations; actual skill, CLI, Core and adapters with evidence sources; checks, outcomes, failures, interventions, assets, recovery and limitations. |
| `runs/<run-id>/reviews/*.md` | Human findings after inspection, linked to request ID, exact code SHA, asset tag/name and session event ordinal. |
| `scenarios/*.md` | Driver-owned product brief and proposed turns, with reviewer guidance separated from actor-visible text. The attempt manifest records what was actually sent. |

`actorOutcome`, `evidenceStatus`, and `reviewStatus` answer different questions. `concluded` means an actor conversation ended; it does not mean the work was correct. A failed or abandoned attempt can have complete evidence. A completed review requires its review file. A structurally valid manifest or a passing moldea `validate` command proves neither correct implementation nor skill activation.

Use one full Git SHA for each source checkpoint and the scenario definition revision. A read-only request can have identical before and after SHAs. Record actor commits separately from driver capture checkpoints. Order requests as delivered; their native event ordinals must increase within each session. For each check, record the exact command or manual method, the input SHA, result, and evidence location or limitation. For each intervention, set `requestId` to the original request and `interventionRequestId` to the later request of kind `intervention`; preserve both results and source SHAs. Link a restarted attempt with `predecessorAttemptId`; do not rewrite the original as an unassisted success. A complete attempt uses known `interventions` and `failures` arrays, with empty arrays meaning none; every intervention request has one lineage record, and a failed outcome has a failure record. It records installation observations in chronological order, one at every native turn-context event ordinal, including repeated contexts for a single request. The verifier checks increasing event ordinals within each session; independent review confirms ordering across sessions. Set `deviation` when either the requested or effective model or effort differs from the run's `expectedActor`; retain the observed values even after a driver correction. The run declares its expected model and effort; the verifier preserves actual deviations without a universal model requirement. This batch selects `gpt-6.1-sol` at `xhigh`. Automatically captured `hostVersion` is provenance, with no version target or standalone completeness requirement.

For a complete attempt, keep a small sanitized identity log as a `kind: "log"` Release asset. Record the actual release verification and installed skill/CLI/Core/adapter composition output, including the method or command that produced each observation. Each `prerequisites` entry and each per-turn `installations` entry has a `source` with the asset `tag`, `name` and a human-readable `locator` into that output. Reuse one log for multiple observations when clear. The verifier requires the referenced log asset and checks its size and SHA-256. Run prerequisites require the selected skill and exact CLI installation target. Core is observed per project, without a run-wide version requirement. The first fully installed observation establishes that attempt's CLI/Core/adapter baseline; subsequent versions and integrities match it exactly. The selected skill ref and content hash stay fixed across every observation. After an initial absent prefix, the first installed CLI must match the run's target. Tooling installed at the start retains its actual baseline; independent review assesses compatibility. `skillRelease` uses the same exact ref as the skill prerequisite. Optional `asset` references on checks and failures, and the required `asset` reference for asset-backed recovery, use `{ "tag": "...", "name": "..." }`; use `null` when no separate asset applies. The verifier resolves non-null references to declared assets by both fields. Reviewers must inspect the cited output to confirm that its contents support the claimed identities and that the published releases meet the required versions; structural verification cannot establish publication or source authenticity. Mark an identity unknown when it cannot be observed rather than copying a requested version into an actual-version field. A complete evidence claim requires these observations.

The per-attempt `redactions` records identify stable rule IDs, reasons, source session ID, event ordinal and field path, and affected persisted locations. Each exported redaction ID must point to that session event and a text field containing `[redacted]`; a complete attempt must account for every declared redaction exactly once. Request `redactionIds` must agree with the sanitized session event. Never store the removed value. When a redaction prevents a conclusion, state that limitation and keep evidence incomplete.

## Fresh adoption observations

Observe tooling before each request using inert root manifest, lockfile, and installed-package metadata. Before invoking an installed executable, follow the selected skill's tooling rules. Record CLI/Core absence as `{ "state": "absent", "reason": "..." }`, supported by the identity log. Inability to observe is not absence. Unknown required facts keep evidence incomplete; never reconstruct the starting installation from the resulting lockfile.

An initial prefix may remain absent through purpose clarification and adoption authorization. The next fully installed observation establishes that attempt's baseline. Link the observed installation result using existing request checkpoints, identity-log sources, and checks that actually ran. No dedicated adoption record or named check type is required. An absent component after a fully installed baseline, or a later identity change, fails complete-evidence verification. Adapter inventories compare by name rather than list order.

A skill-only or diagnostic conversation may conclude with evidenced absence. A failed adoption retains its actual result and linked failure. If adoption finishes without a resulting composition observation, preserve the limitation and keep the record incomplete where verification is missing; do not manufacture a turn or observation. Unexpected repair stays in existing failures, interventions, checks, and limitations until the evidence can support a conclusion.

Check branch, index, scenario, and gallery collisions before naming a project.

Start with a small real-SDK agent product. Use meaningful product changes, unrelated work, and actual SDK execution with a controlled model boundary to inspect activation, silence, context maintenance, and instruction loading. Resume from that worktree with `codex exec resume --model gpt-6.1-sol -c 'model_reasoning_effort="xhigh"' --json <session-id> -`. Supply the actual request on stdin; use its explicit session ID and persisted history. Execution-event stdout is private operational output, not the native transcript. Measure compressed/expanded growth at useful source/request checkpoints. Before expanding the batch, complete evidence verification, independent review, and full website replay of the pilot. The website supports one session asset per attempt and 8 MiB per metadata file and compressed/expanded session. Local-record preview omits replay; full replay uses an authorized public evidence snapshot and a private temporary selection in an isolated website checkout.

Write `observedResult` in plain language around the product result and observed moldea activity or abstention. The website displays it when no recording is available; `observedSummary` and the full timeline are displayed for recorded projects. Explain the skill's contribution in the project summary and existing run review too. ## Capture and privacy

Use Node 24 and `npm ci --ignore-scripts` for the evidence scripts when dependency installation is needed. These scripts do not launch actors, run fixture tests, grade behavior, change Git state, or publish anything.

Select one native JSONL session explicitly. Prepare a JSON redaction file with `includeBaseInstructions` and `rules`. Each rule has `id`, `reason`, zero-based `eventOrdinal`, and a `path` into the **sanitized event** such as `["payload", "content", 0, "text"]`. A whole-field rule replaces its string with `[redacted]`; `start` and `end` select a zero-based, end-exclusive UTF-16 span in the parsed string. The rules contain locators, never secret values. The output root must already exist and be outside excluded directories. Use a portable lowercase name whose complete `.meta.json` sidecar component is at most 64 characters.

```sh
node scripts/evidence/evidence.mjs capture --session <selected-native-jsonl> --redactions <rules-json> --output-root <existing-private-directory> --name <attempt-id>-session-01.jsonl.gz
```

Capture writes a sanitized gzip JSONL file and a `.meta.json` sidecar. The sidecar gives its size/hash, request candidates, event range, redaction IDs and omissions. Native sessions can record delivered requests as either user or developer messages. Copy sanitized request text from the sidecar into the attempt manifest; classify non-task user or developer input envelopes in `ignoredDeveloperEvents`. It is a local drafting aid, not a required published asset. Capture omits encrypted reasoning and host-private world state. When `includeBaseInstructions` is true, it preserves the native base-instruction text whether the host records it as a string or an object with `text`; redact the projected `payload.baseInstructions` as needed. For a natural compaction, it preserves readable replacement messages and retained user messages while flagging an omitted encrypted summary in the event and sidecar. Repeated text in replacement and retained context needs its own redaction rule. The encrypted omission limits any conclusion about the complete context supplied to the actor. Capture also preserves conversation, tool activity and effective turn settings. A completed native `web.search` extension is one tool entry containing its recorded query/action as JSON input and result metadata as inline JSON output; it does not invent a separate call/result pair or retrieved page text absent from native history. Unknown native event shapes stop capture for inspection. Do not claim compaction coverage without a compaction event.

Native function calls retain their namespace/name, argument text and call identity; their separate string results become one text output part. A call's `recorded` status claims capture, not completion. Duplicate clock-completion snapshots are omitted; the function call and elapsed-time result remain. Sub-agent lifecycle metadata appears as JSON host-context messages, which are classified as non-task inputs. Returned agent messages retain their actual body and author/recipient metadata as assistant messages. Non-content delivery metadata is omitted and declared in the sidecar. Explicitly redact encrypted delegation prompts when plaintext is unavailable, retaining that limitation. The parent recording preserves delegation and returned messages; it does not include a separate child's internal history. Distinguish an actor-reported informal check from independently inspected or executed validation.

Before persisting or publishing, review **every** proposed copy: Git history and source checkpoints, scenario and review prose, request fields, manifests, diagnostics, compressed session content, auxiliary logs and recovery assets. Remove credentials, secrets and unrelated machine/session material through explicit redactions before finalizing the capture. Preserve shareable instructions needed to inspect behavior. Inspect the decompressed bytes and the sidecar; rerun capture after any changed rule. Record the human check with `description: "privacy review"` and `inputCommit` equal to the attempt's last durable SHA. Its `coveredArtifacts` must include `evidence/index.json`, the run and attempt JSON paths, the scenario path, every declared asset as `<tag>/<name>`, and `git/<base-sha>/<last-durable-sha>`. That logical Git locator means the full introduced commit range and resulting source state were reviewed, not only the endpoint commit. Include the attempt review path when that review is complete; a completed run review must appear in at least one attempt's privacy coverage. The script validates these coverage locators and declared redactions; it cannot discover arbitrary private information in source or prose or prove the human review happened. Never publish the raw native session or an unreviewed intermediate archive.

## Verify and store

Put small records and source/canonical project history in Git. Put sanitized full sessions, necessary tool logs and exceptional recovery deltas in GitHub Release assets. Do not duplicate complete project histories in archives. Exclude `node_modules`, caches and reproducible builds unless a particular artifact explains a finding. Each asset record stores Release `tag`, exact `name`, size, SHA-256 of downloadable bytes, media type, associated session and event range. For a local check, download assets under `<asset-root>/<tag>/<name>` and run:

```sh
node scripts/evidence/evidence.mjs verify --run evidence/runs/<run-id>/run.json --asset-root <download-root>
```

For the historical run, provide `--asset-root` with the ten downloaded session assets. Verification checks the index and manifests, Git commits/ancestry, request and session locators, effective turn records, evidence status, recovery claims and asset bytes/hashes. It does not audit source correctness, prove privacy, or establish actor behavior. An incomplete run can pass structural verification while remaining explicitly incomplete.

Use portable lowercase path components for generated evidence names and paths. Recovery inventories preserve existing source paths such as `README.md` and `.agents/skills/moldea/SKILL.md`; the verifier still rejects traversal, escapes from the repository root, and paths under `_archive`, `_archives`, `_backup`, or `_backups`. Do not include credentials, private machine paths, or unrelated native-session content in names or records. Generated evidence paths also reject reserved names and symlinked repository files; referenced lists reject case collisions.

The storage choice follows measurements of the existing 14 attempts: their native sessions total 28,201,688 raw bytes and 7,375,435 gzip bytes (about 7 MiB); individual compressed sessions range from 105,823 to 1,026,579 bytes. Representative project trees contain 26–75 files and about 1.09–1.16 million uncompressed blob bytes, of which about 940 KB is shared installed skill content that Git can deduplicate. Ten or 100 repetitions of the observed 14-session workload would add about 70 or 700 MiB of compressed session assets, before other logs or workload changes. Measure actual Git and asset growth after later runs; this estimate is not a project-count limit.

GitHub [warns above 50 MiB per ordinary Git file and blocks above 100 MiB](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github); it recommends repositories ideally below 1 GB and strongly below 5 GB. Its [repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits) separately recommend 10 GB on disk and enforce a 2 GB push limit. A [Release](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) may hold up to 1,000 assets, each under 2 GiB, with no stated total release-size or bandwidth limit. These are operational guidance and limits, not an implied retention policy. Keep the small, reviewable records in Git and bulky evidence in assets; do not add a database or destructive cleanup for hypothetical scale.

## Interrupted attempts

Stop writes before capturing the reached source state. Prefer a signed driver checkpoint commit that preserves unfinished tracked and untracked work, deletions, modes and relevant binary files without repairing the actor result. The `recovery` record identifies the preceding base SHA, checkpoint SHA, path inventory, restoration procedure and verification result. Verify a disposable checkout and its inventory before setting `verified: true`. The verifier compares a verified checkpoint inventory with its Git diff and file hashes. The passed `recovery restoration` check must use the checkpoint SHA as `inputCommit`, include `git/<base-sha>/<checkpoint-sha>` in `coveredArtifacts`, and use `asset: null`.

If a commit is blocked, make a sanitized recovery asset containing the delta from `lastDurableCommit`, including new files and deletions. Record its exact tag/name reference, hash and path inventory. Restore it in a disposable checkout, record a passed manual check with `description: "recovery restoration"` and any gaps, and keep the original worktree until durable storage is confirmed. That check must use the recovery base SHA as `inputCommit`, include `<tag>/<name>` in `coveredArtifacts`, and cite the same asset tag/name in `asset`. The verifier checks asset integrity and that matching restoration check; the reviewer must inspect the actual restored result. A transcript plus an earlier SHA cannot recover uncommitted source. If material is missing or redaction prevents recovery, set `verified: false`, list the gaps and keep the attempt incomplete.

An interrupted attempt always has `evidenceStatus: incomplete`. Record the captured event range and what remains unavailable. A later resumption retains its real session and turn settings; a fresh restart or retry gets a new ID and predecessor link. A correction delivered in the existing conversation remains a recorded intervention in that attempt.

## Public export contract

A later authorized public export uses the **same** `index.json`, run/attempt JSON and review Markdown, the shareable Git refs/history and the same sanitized asset bytes. A website can fetch the static index, follow manifest paths, display findings and availability, link full SHAs to code, and construct Release downloads from the public repository plus each tag/name. No second format, database, service, webhook or automatic website publishing is needed. Audit history before export. If required redaction changes Git SHAs, mark those links unavailable pending a separate reviewed export decision; do not invent equivalent public commits.
