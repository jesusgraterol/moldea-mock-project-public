# Mock project conversation plan

## Objective and role

Build a collection of believable mock projects on numbered branches of this private repository. A developer driver presents each product need to a separate coding-agent session with the repository-installed Moldea skill. The driver starts with a small brief, answers actual questions, and sends ordinary follow-up requests as distinct session messages. The coding actor builds the project and uses the skill. Those actor sessions and branch histories are the evidence for a separate observing agent to audit.

The driver and coding actor preserve the real conversations, errors, branches, and factual outcomes without grading the skill or repairing canonical files to meet a fixture target. Complete the authorized first pass before the developer asks the agent in the skill repository to review all evidence. That agent determines whether adjustment is warranted; an observed failure alone does not justify changing instructions.

The deliverable is the attempted project branches, real development histories, and concise `main` index. These are source-only prototypes with plausible product facts and inspectable instruction-loading and invocation paths. Deliver the construction constraints in each actor's brief as specified below, and preserve incomplete integration honestly. Connection, Assurance, and resolution-prompt testing remain the developer's separate manual work. Do not edit sibling skill, package, or platform repositories.

Do not create deliberately broken `partial` or `invalid_binding` branches. A naturally occurring incomplete or invalid state remains valuable evidence and must be preserved honestly.

## How each attempt proceeds

1. Choose the numbered branch and confirm its product brief. Resolve the latest stable published skill and required libraries for that attempt, reusing current release research from earlier attempts when applicable. Pin the selected direct dependencies exactly in the project manifest and lockfile. Keep those versions fixed during the attempt; a later release is a reason for a new attempt, not an automatic update of old branches. Let the skill establish the repository-local CLI at the point its workflow calls for it.
2. Create the numbered branch in its fresh worktree from the recorded initial commit. For product scenarios, the driver creates a small product README and initial fictional records, then commits that preparation before starting the actor. Include the source-only prototype constraints explicitly in the actor's brief: no working service, deployment, credentials, live provider execution, or application test suite is required. Request small, plausible source with meaningful instruction-loading and invocation paths, and honest notes about incomplete integration. Confirm that planning/index commits have not entered the ancestry. Do not pre-author the Moldea foundation, a complete agent roster, or adapter-shaped implementation; the actor develops the source using current official SDK APIs.
3. Install the skill in the attempt's worktree using its published repository-scoped instructions. Start a separate actor session bound to that worktree, with no inherited driver or other-project turns, and deliver the intended existing repository instructions through the host without changing protected files. Confirm selection of this worktree's installed skill before a skill operation; installation alone does not establish activation. Use the documented host entry path or report the attempt stopped if selection fails. Do not substitute a global skill or sibling checkout.
4. Send each developer request as a distinct message and let the actor respond using the installed skill. Request adoption in ordinary terms such as `Initialize moldea`, then answer actual product questions. Later requests describe product work without reminding the actor to update Moldea or prescribing canonical destinations. Keep explicitly read-only discussion separate from later implementation authorization, and react naturally when work reaches a relevant adjacent module. Do not write a request and its supposed response within one actor turn.
5. For source-bearing projects, continue past initialization and initial capability creation. Introduce at least one meaningful follow-up grounded in the observed intermediate state or a plausible new requirement. The actor makes the corresponding source and product changes, while the installed skill decides whether and how to maintain canonical state. Where complex role division is useful, ask the actor to invoke the skill's read-only agent-system planning workflow after adoption.
6. Commit coherent stages so the observer can inspect the brief, adoption, and refinement. Retain exact requests, responses, meaningful tool results, errors, and naturally occurring compaction evidence in the native session. Do not manufacture a transcript, force compaction with a long conversation, or assert behavior the skill did not exhibit. Add turns only when product needs or the assigned conversational situation justify them; there is no fixed turn count or agent quota.

The driver may react to an actor's output as an ordinary developer, while the actor may correct its own source mistakes or ask the skill for a supported repair. Preserve the initial error and subsequent actions in the actor session and branch history. Do not hand-write canonical content merely to satisfy a fixture target. When a project-specific skill or compatibility problem needs an external change, stop that attempt at the observed state, record the blocker, and continue the remaining independently authorized projects. Do not pause the first pass for project-specific skill tuning or repeat that attempt on the builder's initiative. Apply the shared prerequisite rule above when the same blocker prevents every project from starting.

After the full first-pass handoff, the developer asks the skill-repository agent to review the complete evidence. That agent determines whether a skill adjustment is warranted; failures alone do not establish that its instructions are wrong. If an adjustment is warranted, it is made and released from the skill repository. The developer then authorizes the next run, and the skill-repository agent reviews that evidence again. The driver preserves evidence and executes authorized runs without tuning the skill, issuing quality verdicts, or initiating reruns.

For a developer-authorized full rerun of all projects or a selected subset, use each project's next numbered branch, a fresh disposable worktree from the recorded initial commit, recreated unadopted briefs, and a fresh actor session. Select the published releases at the new attempt's start and deliver the distinct developer requests again. Preserve earlier attempts and record meaningful input or dependency differences. Initialization and later maintenance must both be exposed to the selected skill.

For a separately authorized focused replay, use the next numbered branch in a fresh worktree from the recorded commit immediately before the selected request. A maintenance replay may inherit committed adopted state, but no leftover filesystem state. Record the starting SHA and new setup checkpoint, and state that the newer skill performed only the replayed operation, not inherited initialization. Neither rerun form is automatic.

## Records and publication

Keep records small. A project's README describes the fictional product, a named mock case, the installed skill release and path, the base commit, any retry parent, and the observed stopping point or limitation. Source-bearing projects also describe the later product change. Exact dependency versions belong in the manifest and lockfile. Each actor session carries its detailed requests, answers, tool results, and errors for the observing agent.

On `main`, maintain one concise table with scenario, attempt branch, date, skill release, commit SHA, actor-session reference, and a factual note such as `initialized`, `continued through policy change`, or `stopped during installation`. Retain the actual actor model, reasoning setting, host version, and installed skill release through reliable native session metadata or this index. Add only metadata missing from those existing records; do not duplicate reliable metadata or infer settings from defaults. Do not mark attempts `passed`, `failed`, or approved for manual testing. Retain concluded attempts even when they expose problems.

Before a commit, inspect the intended changes and exclude unrelated user files, secrets, and protected instructions. Use cohesive commits with both required `-s -S` flags; do not bypass hooks or signing. Publish only the active attempt branch to the verified private `origin` destination with an explicit one-branch refspec, without force or tag following. Compare the resulting remote ref with the local reviewed commit, then add its SHA and factual note to `main`'s index and publish that update. Preserve a branch locally and report the blocker if a conflict, unsafe change, signing problem, or remote failure prevents publication. Do not hide an observed skill problem to make publication easier.

The chronological driver conversation and linked actor sessions provide the audit trail across projects and milestones. Keep stable session references in the index so the observer can follow the full run without a reconstructed transcript. Do not add a fixture generator, evaluation rubric, scoring system, observer integration, CI matrix, or dedicated report package.

## Verification and limits

The driver checks worktree targeting, host-delivered instructions and brief constraints, retained runtime metadata, local skill selection, releases, branch/base/ancestry, diff, signatures, and remote SHA. Keep source fictional and non-sensitive. Use `git diff --check` and existing targeted formatting. Run CLI validation or TypeScript checks only when called for, preserving actual output without repeated diagnostics or cosmetic repairs to canonical state. No application tests or provider execution are required. These checks do not certify skill quality.

Use fictional non-sensitive data only. Keep source small enough to understand a case, its relevant rules, and the later change. There is no persistence, authentication, migration, deployment, or external runtime to operate. Follow repository path and naming rules for new files and branches. Do not claim that a structurally valid manifest proves the skill worked well, or that an unrun provider flow works.

The first pass is complete when all 14 scenarios have recorded attempts and accessible native sessions, and safely publishable branches and the index are on `origin`. Record reached conversational situations, incomplete integration, and blockers factually. Hand the complete evidence to the developer for the skill-repository agent's review, without a quality verdict or automatic rerun.
