# Mock project fixture plan

## Objective and scope

Build a private, branch-per-project fixture corpus in this repository for later manual testing of `moldea` repository connection and, when available, PR Assurance and resolution prompts. The deliverable is the published Git branches and their understandable project content. This plan does not connect the repository to Cloud, change the GitHub App, open PRs, run Assurance, generate resolution prompts, or modify the sibling `platform`, `skill`, or `packages` repositories.

The coding agent will build each valid branch as though carrying out a sequence of ordinary developer requests for a plausible fictional product. The branch outcome is synthetic; the build process uses the actual installed skill when the developer would initialize project context, plan agents, add capabilities, or maintain existing relationships. The agent must not pre-author all source and agent structure and then ask the skill to document a foregone design. README, source, canonical context, instructions, and relationships must tell the same story, including one small later requirement change on each source-bearing branch. Projects need no working server, credentials, provider calls, database, application tests, or deployable build. Valid branches must have syntactically credible source and pass skill validation; deliberately broken branches must fail for their one documented reason.

It has no package manager, application source, installed skill, or `/moldea/**` state. The local `AGENTS.md` is ignored and protected; do not edit or commit it.
- The sibling skill checkout identified release `5.0.13` during planning. `../skill/docs/getting-started.md` and `../skill/docs/compatibility-and-local-tooling.md` require repository installation, a repository-local compatible `@moldea.ai/cli` development dependency for deterministic operations, a two-file minimum canonical foundation, and the managed README block. `../skill/docs/planning-agent-systems.md` requires initialization before repository-dependent agent-system planning and allows a zero-agent recommendation. `../skill/docs/coding-agent-compatibility.md` distinguishes an installed copy from actual coding-host activation. Recheck the latest published tag and compatibility contract at implementation start because releases are frequent; the planning snapshot is not the fixture version.
- `../skill/qualification/profiles/index.yaml` has ten official package-backed adapter IDs plus built-in `custom`. Cloudflare Agents, LangGraph, and Vercel AI SDK each have two qualified target forms. The qualification profile READMEs describe supported source patterns and previously tested package versions. The current compatibility snapshot gives minimum eligible versions, but eligibility does not prove that a newer release's source API still matches the adapter. Use the latest stable published library versions at implementation time and inspect actual installed package contracts and adapter evidence.
- `../packages/specifications/repository-format.md` requires one `/moldea/**` project root, existing files for declared bindings, agent `description.md` and `instruction.md`, and a runtime ID for each registered agent. It has no manifest-owned handoff graph. Runtime-native handoffs must be represented by real source wiring and, where useful, target-owned `handoff-description.md`.
- `../platform/README.md`, `../platform/moldea/context/cloud-and-assurance.md`, and `../platform/docs/repository-testing.md` establish that repository linking exists, the customer-facing hosted PR Assurance workflow remains feature-gated, and the separately pinned live repository test lane targets another private repository. No step in this plan changes or relies on that lane.

## Fixture structure and branches

Use `snake_case` branch names. `main` remains unadopted and contains a concise fixture index and update instructions in its existing `README.md`, with no skill or `/moldea/**` files. Create `fixture_skill_only` from `main`; it contains the repository-installed current skill but no canonical project, managed README block, or CLI dependency. Every other fixture branch descends from `fixture_skill_only`, so a later skill refresh needs one installation commit and ordinary merges into the fixture branches. Do not introduce an updater script, CI matrix, fixture generator, or shared runtime package.

The coverage goal is an acceptance condition, not a prewritten agent roster or canonical schema. The skill and the evolving project determine source filenames, agent IDs and count, context topics, tools, bindings, and runtime guidance. For the three adapters with two target forms and the native delegation branches, the developer request must genuinely support that coverage. If the skill finds the proposed split artificial, improve the product request and implementation coherently or report the gap; do not manufacture an agent or relationship for a passing inspection. Every adopted valid branch owns a concise product README, `package.json` and `package-lock.json` for an exact-pinned repository-local CLI and needed runtime packages, the skill-managed README block, `moldea/moldea.yaml`, and `moldea/project.md`. Every source-bearing branch also owns the smallest coherent TypeScript source, `tsconfig.json`, exact-pinned latest stable TypeScript, and only required type packages. Agent `description.md` and `instruction.md` files exist for registered agents; focused canonical context and optional handoff descriptions exist only when justified. `fixture_initialized` needs no source or TypeScript. The negative branches inherit their valid parent's files and document the single defect. No application tests, empty directories, filler documents, framework shells, or unrelated infrastructure belong in these fixtures.

For each source-bearing valid branch, the final README includes one representative user request and expected outcome tied to a specific mock record and policy or instruction. It also describes one later, ordinary requirement refinement and the resulting behavior. These are product facts a human can follow across source and canonical state, not a fabricated conversation transcript. The actual local branch history should make the sequence visible through a small initial product/adoption state followed by the refinement; keep commits cohesive and signed. Cedar Workshop stops after skill initialization, so it has no refinement. The negative branches inherit their parent's history and add only their deliberate mutation.

At implementation time, resolve npm's latest stable versions for every direct runtime library, necessary peer, repository-local CLI, TypeScript, and any required type or Zod package; pin exact versions in the manifests and lockfiles. The qualification pins are source-pattern examples, not fixture dependency choices. If a latest stable release is outside the skill's compatible range, cannot install with current peers, or has an API the adapter cannot recognize, report the exact mismatch and stop that branch for a plan decision rather than silently downgrade, switch runtime ID, or claim a valid fixture.

## How the skill must be used

1. At implementation start, establish the latest published skill tag and its compatible CLI range. Install that exact tag into `fixture_skill_only` with the documented repository-scoped `npx skills add` command. Verify that the latest stable repository-local CLI is compatible, and inspect the installed `SKILL.md` and installer paths. After installing and after each valid-branch checkout or skill refresh, confirm through the coding host's supported skill discovery or invocation mechanism that it selected that branch's repository-installed skill path and version before a skill-dependent request. File presence, a manually read `SKILL.md`, and a successful CLI call alone do not establish host activation. If the current session cannot discover the installed copy, re-enter the branch in a compatible session or host; stop that branch if activation still cannot be verified. Never substitute a global skill or the sibling checkout.
2. Treat the branch table as developer intent, not as a recipe for Moldea files. Build a small first product slice in the selected runtime using current public APIs: product purpose in README, a few typed mock records and domain rules, and a representative user request with an expected result. For `fixture_initialized`, the developer's product brief alone supplies the foundation and no source is written. Do not prewrite a manifest, agent instruction, or adapter-shaped snippet solely to satisfy a profile.
3. At the natural adoption point, invoke the host-selected repository skill with `Initialize moldea` against the product evidence. Record the selected installed path and version along with the operation and result. Let it create the foundation and managed README block, and review the skill's actual output and diff. If it needs a product decision, resolve the fictional developer requirement coherently before proceeding; do not invent a canonical answer unsupported by the request or source. A failed skill operation remains a reported failure, not a cue to hand-author canonical state while claiming success.
4. After adoption, continue as a developer requesting the next feature or agent capability. Use the installed skill's planning workflow first where the division of work matters, especially on Harbor Supply; its repository-dependent planning requires the initialized foundation and is read-only. Let the skill distinguish deterministic software, runtime tools, model reasoning, and human control before the coding agent implements source and skill-maintained context/agents together. Read the installed adapter contract and actual latest library API before relying on a runtime relationship. The skill may recommend fewer agents than anticipated; revise the product need only when a genuine workflow warrants additional roles.
5. After reviewing the adopted feature, commit that coherent baseline with `-s -S`. Give every source-bearing valid branch one modest follow-up developer requirement within its domain, such as a new exception, policy detail, or record state. Make the source change as an ordinary project edit while the installed skill is available, let its relevance and maintenance workflow update affected canonical state, review the before/after diff for both source and Moldea, then commit the refinement with `-s -S`. This preserves real project progression without a test harness, scripted fake dialogue, or extra product machinery.
6. For each branch, typecheck source against exact installed SDK versions, run skill validation and adapter inspection, and review the actual project story. Accept only existing source relationships and useful instructions. If a tool, handoff, schema, policy, or binding lacks evidence, correct the project and rerun the skill or report the gap. Do not invent a file path, symbol, provider behavior, or policy just to make validation pass.
7. Build the two negative branches only after their valid parents pass verification. Make one deliberate mutation per negative branch, capture the expected diagnostic, and leave the skill-built parent intact. Those faults are the only manual canonical edits authorized by this plan.

Keep `fixture_skill_only` as the single source of the installed skill bytes. For a new release after the publication cutoff, verify the current published tag, rerun the documented repository-scoped installer there, inspect its diff and metadata version, and commit it. Merge that commit into each fixture branch, confirm the coding host selects the refreshed branch-installed version before skill-dependent work, update a branch's repository-local CLI if the new skill requires it, rerun the branch's relevant validation and source typecheck, and commit the refresh. Update `main`'s recorded version and new UTC cutoff for that refresh. This uses ordinary Git and the official installer, with no custom updater. Releases after the recorded cutoff do not retroactively make the published snapshot stale; they enter through this refresh. A release that changes repository format, adapter targets, or supported CLI contracts requires a focused plan revision before changing fixture semantics.

## Risks, exclusions, and publication boundary

- Adapter static analysis recognizes specific source forms and package ranges. A latest stable library version inside a published range is eligible for inspection but may differ from the exact version previously qualified. An apparently plausible SDK snippet can still be unsupported or fail against the installed SDK; use the installed library contract, local typecheck, and adapter inspection result, and report unresolved evidence rather than reclassifying it as `custom` or downgrading the library without a new decision.
- A project can be structurally valid while its source and instructions disagree. Human content review and inspection of the build sequence are required; validation alone is insufficient. The simulated developer requests are deliberately concise and may need a focused fictional product decision during implementation. Resolve such decisions from the established branch intent without fabricating provider behavior, credentials, or customer facts.
- Skill installation, npm manifests and lockfiles, branch commits, and remote branch publication are intentional changes within this plan. Inspect their generated bytes and paths. If the installer creates host-specific duplicates or protected instruction files, stop before committing and resolve the installation path without editing protected files.
- Existing GitHub App installation scope, Cloud project authorization, and hosted Assurance availability are outside this plan. Publishing fixtures makes them available for later manual testing but does not establish that those external flows work.
- The planning directory and ignored local `AGENTS.md` are outside fixture commits. Do not stage or publish them inadvertently. Do not add CI, automation, runtime services, migrations, deployment files, or PR scenario branches.
